# Gaming

**Date:** 2026-10-26
**Status:** planned, on `main`

A game in front of the shell has to get the output to itself: nothing the
shell maps over a fullscreen window (that drops Hyprland's direct scanout and
re-blurs the game every frame), no work behind it, no screensaver while a
controller is the only input, and no VRR setting the shell rewrites. The
launcher, switcher and polkit still come up over it on demand. Steam,
gamescope and Proton need what a KDE install gave them: a portal, a
ScreenSaver inhibit service, controller udev rules.

The owner's report: on the Quickshell build a notification arriving lag-spiked
games. Here the same shape exists: `present_toasts` maps a whole-output
overlay layer per burst and commits every frame while it animates, with no
fullscreen check (`wayland/toasts.rs:111`).

One subagent per task, sequential, each ending in its verification run read
back and one commit. The tree carries another agent's staged wallpaper-depth
work: every commit names its own paths (`git commit -- <paths>`), never the
whole index. VM work goes through `dev/vm-lock.sh just vm-smoke <flags>`.

## Task 1: what counts as fullscreen

- `services/compositor/hyprland/model.rs:92`: an output is covered when the
  active workspace of that monitor holds a window with fullscreen mode 2
  (bit 2 of Hyprland's `fullscreen`/`fullscreenClient`), focused or not, or a
  window whose rect equals the monitor's rect (a borderless game). Mode 1
  (maximized) no longer hides the bar. Mango's model gets the same rule where
  it has the data.
- Check: unit tests over captured `clients -j`/`monitors -j` fixtures for each
  case; `--fullscreen` and `--multi-output` legs.

## Task 2: nothing over a covered output

- Toasts still show over a fullscreen game (owner, 2026-10-26), but today
  the owner's report: with a game holding the cursor locked, a toast
  appearing unlocks it, with no input at all. A locked or confined pointer
  only holds while the game's surface has pointer focus; the likely cause is
  the stack's whole-output layer mapping with the default (infinite) input
  region before `sync_region` narrows it, so Hyprland's refocus on map hands
  the pointer to the toast. Find the actual cause in the code before fixing.
  On a covered output the stack is mapped with an empty input region from its
  first commit and keyboard interactivity none. The toast layer
  is sized to the stack and anchored to its corner instead of covering the
  output, so a toast over any game allocates and damages a card's worth, not
  a screen's, and stays unblurred.
- OSD: not mapped on a covered output.
- Polkit: `Layer::Overlay` like the launcher, so a prompt raised mid-game is
  seen rather than taking the keyboard behind it.
- Check: `--notify`, `--toast-motion`, `--notify-emerge --pantheon`,
  `--osd`, `--polkit`, `--fullscreen` (extended: a toast under the
  fullscreen fixture maps a corner-sized layer with an empty input region,
  the pointer stays on the fixture window, `hyprctl cursorpos`/`activewindow`
  unchanged; an OSD call maps no layer).

## Task 5: org.freedesktop.ScreenSaver

- The shell owns `org.freedesktop.ScreenSaver` on the session bus at
  `/org/freedesktop/ScreenSaver` and `/ScreenSaver` (`Inhibit`, `UnInhibit`,
  `GetActive`), without replacing an existing owner. Each cookie holds the

**Title:** scrolling: any layer surface map drops every pointer constraint when the workspace has no fullscreen window

Hyprland v0.56.2, `general.layout = "scrolling"`. A client holds a
`zwp_locked_pointer_v1` (a game, floating: borderless at the monitor's
size, or in fullscreen). Any layer-shell client then maps, unmaps or
changes the layer state of a surface on that monitor (a notification
daemon showing a toast is enough). The lock is deactivated and stays off
until keyboard focus leaves the window and comes back.

Cause: `CLayerSurface::onMap`/`onUnmap`/`onCommit` call
`arrangeLayersForMonitor`, which reaches `invalidateMonitorGeometries`
(`Renderer.cpp:2701`) and recalculates the workspace
(`LayoutManager.cpp:357`). The scrolling recalc ends in
`updateFullscreenFade(TARGET_WORKSPACE_HAS_FS)`
(`ScrollingFullscreenHandler.cpp:635`), and with no fullscreen target that
branch calls `g_pInputManager->unconstrainMouse()` (`:705-707`), which
deactivates every constraint on the seat (`InputManager.cpp:1808`).
A constraint only comes back on a keyboard focus change onto its surface
(`FocusState.cpp:266`).

`TARGET_WORKSPACE_HAS_FS` only counts tiled scrolling targets in
fullscreen or maximized mode (`ScrollingAlgorithm.cpp:507-510`), so a
floating window in real fullscreen (mode 2) hits the same unconstrain. A
tiled fullscreen window holds its lock through the same toast.

Expected: only unconstrain when a fullscreen window is actually being
faded out (a transition away from fullscreen), not on every recalc, and
never a constraint the layout does not own.

Repro: scrolling layout, any pointer-lock client floating and focused,
either resized to the monitor or fullscreened, then `notify-send hi` under a layer-shell notification
daemon.
