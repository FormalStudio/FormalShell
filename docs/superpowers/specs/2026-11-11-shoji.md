# FormalShell on ShojiWM

Date: 2026-11-11. Owner's call: the Hyprland session (a scrolling tape made
to behave like niri, with the overview, zen and the console bolted on from
the shell over `hyprctl`) is rebuilt on ShojiWM, where the window manager is
a program we own. Hyprland stays installed and stays the default session
until the owner switches.

ShojiWM (github.com/bea4dev/ShojiWM, our fork FormalSnake/ShojiWM, branch
`formal`) is a Smithay compositor with no window manager in its core. A
config decides every window's rect, workspace, decoration and animation,
composes the output from live window textures, takes input grabs, and
serves its own JSON socket. The config is TypeScript in an embedded V8 by
default, or a Rust crate on `shojiwm_rs` that compiles into its own
compositor binary. Ours is Rust (owner's call, 2026-11-11): no V8 in the
compositor, no garbage collector or runtime boundary on the frame path, and
the engine shares the wire types with the shell.

## 1. Who owns what

| Thing | Under Hyprland | Under Shoji |
| --- | --- | --- |
| Tape layout, workspaces, rules, binds, gestures | `hyprland.lua` in the owner's spec | `wm/` in this repo (the engine, the compositor binary `formalwm`) plus a settings file in the spec, read at start and on reload |
| Overview | the shell's surface, thumbnails captured per window | the compositor: live textures, section 4 |
| Zen | the shell floats the window and shoves the tape off screen | the compositor: a layout mode of the tape, section 5 |
| Console | a Hyprland special workspace | an overlay workspace of the engine, section 6 |
| Drag and drop | none across workspaces outside the overview | section 7 |
| Theme | two Lua files and `hyprctl reload` | `theme.set` over the socket, no file, no reload |
| Bar, sidebar, minimap, menus, lock, capture, switcher | the shell | the shell, through the `shoji` backend |

The shell keeps one compositor door (`services/compositor`). `shoji/` is its
second backend beside `hyprland/`. The mango backend (added dd6c7868,
removed fcf537df) is the template for how a second backend sits there.

## 2. The engine: `wm/`

A Rust crate on `shojiwm_rs`, in its own cargo workspace under `wm/` (it
links Smithay, libinput, gbm and libseat, which the shell's Debian build
image is too old for, so it is a store package of its own built on
Tumbleweed). Its binary, `formalwm`, is the compositor. `shojiwm_rs` and
`shojiwm_lib` come from the fork by git rev.

A Rust config has no hot reload, so what the owner changes is data, not
code: workspace names, per-host outputs, window rules, binds, the terminal,
input settings live in one settings file (`~/.config/formalwm/`, from the
spec's home tree, in the format the shell's own settings use), read at
start and read again on the control socket's `reload`. A bad file keeps the
running settings and reports the error. An engine change is a package bump
and a new session.

The wire types of section 3 are one crate, `crates/fs-wm-proto` (serde
only), that the engine and the shell's backend both depend on. The
`outputs` of `State` are its `StateOutput`, the rows of `outputs.get` its
`Output`.

It starts from the Rust port of ShojiWM's previous default config
(`src/shojiwm_rs/examples/default_config`) and the current TypeScript one
(`packages/config/src`), which have a floating mode, a one-window-per-tile
scrolling row, kinetic three-finger scrolling, workspace switching, a JSON
socket and the window switcher's composition. Where `shojiwm_rs` lacks
something the TypeScript SDK has, it is added to `shojiwm_rs` (section 8).
What the engine must be is the tape in `hyprland.lua`:

- Columns of stacked windows. Default column width 0.5 of the output,
  presets 0.333, 0.5, 0.667, 1.0, a lone column keeps its width and is
  centred. Focus fits the focused column into view by the least scroll, it
  does not recentre.
- 8 px between everything: 4 per window side, 8 at the output edge, from
  the theme (`gapsIn`, `gapsOut`). Gaps are measured to the outer edge of
  a window's border, as Hyprland's are: a window's content starts
  `gapsOut + borderSize` inside what the layers leave free, and two
  windows' contents are `2 * gapsIn + 2 * borderSize` apart.
- Nine workspaces per the spec's names, stacked vertically, a workspace
  switch slides vertically. A workspace can be pinned to an output by the
  host settings.
- Focus changes on click only; the hovered window still gets pointer
  events.
- `focusedWindowId` names the window that has the keyboard. The engine
  asks the compositor for the model's window on request (P14) and then
  takes what the compositor answers: a focus it refused or gave to
  another window in view is not kept, and a press on the window that had
  the keyboard all along puts the model right.
- Every bind in `hyprland.lua`, same chords. The es layout's number row is
  bound by keycode (core patch P2) so the shifted variants hold. A chord
  runs every bind it has, each by its own flags: on the lock screen only
  the ones marked `locked`, on a held key's repeat only the ones marked
  `repeat`. A bind on a modifier let go runs when the modifier was pressed
  and let go alone. After a chord that used the modifier it runs only when
  it is marked `passthrough` (Hyprland's `transparent`) and holds the
  modifier it is on (`ALT+Alt_L`): as under Hyprland, a bare `Alt_L`
  matches no modifier state a chord leaves behind.
- The `mac` submap of `hyprland.lua`, as `binds.handOver`: while a Mac
  window has the keyboard the binds on Super alone and on Super with Shift
  are off the keys, so the chords reach the app as Command, save the ones
  `macApps.reservedBinds` keeps. A pointer button, the wheel and every
  chord with Ctrl or Alt stay bound. The shell names the window; the
  engine holds it over that window alone, with every bind back whenever
  another window, a layer surface or the lock screen has the keyboard and
  under the overview, and ends it when the window closes or the shell's
  connection does.
- Three-finger horizontal drags the tape 1:1 and flings on release; three
  fingers vertical walks workspaces and keeps going past the neighbour.
  Four fingers up opens the overview.
- The window rules in `hyprland.lua` as a table of matchers (app id, title,
  xwayland, toplevel tag, floating) to workspace, float, pin, size,
  position, opacity, and `confinePointer`: the pointer stays inside the
  window while it has the keyboard (Hyprland's `confine_pointer`).
- The dynamic cursor of `hypr-dynamic-cursors` as `hyprland.lua` sets it,
  `cursor.dynamic` in the settings: the image stretches along the way the
  pointer travels (`mode` `stretch`, or `tilt`, or `none`) and grows while
  it is shaken. Off on the lock screen and while the cursor is hidden, and
  no transform at rest.
- Motion from the shell's six clock families (`theme.set`, `chrome.motion`):
  anything with a position or size rides a spatial curve, opacity and
  colour an effects curve.
- Blur and alpha threshold per layer namespace, as the layer rules in
  `hyprland.lua`, and no compositor animation on any `formalshell:*` layer.
- A settings reload keeps every window where it is.

## 3. The socket

ShojiWM's own transport (`shojiwm_rs::ipc`, the same wire as the
TypeScript SDK's `createIpcServer()`): a Unix socket at
`ipc::default_socket_path()`, `$XDG_RUNTIME_DIR/shojiwm-$WAYLAND_DISPLAY.sock`,
newline-delimited JSON. A request is
`{"id"?, "method", "params"?}`; an answer `{"id", "result"}` or
`{"id", "error"}`; a broadcast `{"event", "payload"}`. A request without an
id is a command with no answer.

`$SHOJIWM_SOCKET` is not this socket: `shojiwm_lib`'s `control_socket.rs`
exports it for its own one-line `quit` and `reload` socket at
`$XDG_RUNTIME_DIR/shojiwm.$WAYLAND_DISPLAY.sock`. The engine never binds
`$SHOJIWM_SOCKET` (a bind removes the file first, which would take quit and
reload away). The shell's backend picks Shoji when `SHOJIWM_SOCKET` is set,
Hyprland when `HYPRLAND_INSTANCE_SIGNATURE` is, and under Shoji connects to
the JSON socket's path, which it derives the same way. The socket going
away (the compositor restarting) is the compositor unavailable; the shell
reconnects with a backoff.

### State

`state.get` answers `State`; `state.changed` broadcasts it, coalesced to
one per tick and dropped when its JSON equals the last one sent.

```ts
type State = {
  version: 1;
  outputs: {
    name: string; x: number; y: number; width: number; height: number; scale: number; enabled: boolean; // logical
    reserved: { top: number; right: number; bottom: number; left: number }; // what the layers' exclusive zones take from each edge, logical
  }[];
  workspaces: {
    id: string; idx: number; name: string; output: string;
    active: boolean; focused: boolean; urgent: boolean;
    columns: boolean;          // false for a floating workspace
    zen: string | null;        // the window in zen, section 5
  }[];
  windows: {
    id: string;                // the ext-foreign-toplevel-list identifier
    title: string; appId: string; initialAppId: string; initialTitle: string;
    tag: string;               // the client's xdg-toplevel-tag, "" where it set none
    pid: number;
    workspaceId: string;       // "" on an overlay
    overlay: string | null;    // the overlay it lives on, section 6
    shown: boolean;            // an overlay window currently on screen
    focused: boolean; floating: boolean; fullscreen: boolean; urgent: boolean;
    column: number; row: number;   // -1 when floating
    rect: { x: number; y: number; width: number; height: number } | null; // global logical, where the layout puts it, not a frame of its animation
  }[];                         // in first-seen order
  focusedWindowId: string; focusedWorkspaceId: string; focusedOutput: string;
  overview: boolean;
  keyboard: { layouts: string[]; active: number };
  cursorHidden: boolean;
  chrome: { gapsOut: { top: number; right: number; bottom: number; left: number }; borderSize: number; activeBorder: string; blur: boolean };
  handOver: { window: string; reserved: string[]; active: boolean } | null; // what `binds.handOver` holds; active while the window has the keyboard and its chords are off the binds
};
// activeBorder is "#rrggbb" or "#rrggbbaa", the focused window's border.
// borderSize is the border's width in logical px, drawn outside a window's rect.
```

`id` being the foreign-toplevel identifier is what lets `wayland/capture.rs`
key a capture by window id with no Hyprland mapping protocol.

It ends on `on` false (whatever `window` says), on another `on`, when the window closes, and when the connection that asked closes, so it is sent on the connection the shell keeps and again after a reconnect. `State.handOver` follows. | `cursor.pos` | answers `{x, y}` global logical | `cursor_pos()` |
| `cursor.hide` | `{hidden}` | `Cursor` |
| `layers.list` | answers `{namespace, output, layer, x, y, width, height, pid}[]`, every mapped layer surface in stacking order (the bottom first), `layer` one of `background bottom top overlay`, the box global logical, `pid` 0 when the engine does not know it | the rig's `$wmctl_bin -j layers` |
| `outputs.get` | answers `Output[]`, every output, disabled ones too (below) | `RefreshOutputs` |
| `outputs.set` | `{name, enabled?, scale?, mirror?: string, color?: Color, width?, height?}` (`mirror` "" stops mirroring). `width` and `height`, the mode's pixels, only on an output `outputs.create` made: it is resized in place, its layers are told the new size and none is closed. An error on any other output | `SetOutput*` |
| `outputs.create` | `{name?, width, height, scale?}`, answers `{name}`: an output with no connector, made while the session runs (P11). From then on an output like any other: in `State.outputs` and `outputs.get`, with workspaces of its own, and `state.changed` follows. `width` and `height` are the mode's pixels, `scale` 1 when absent, the engine names it when `name` is absent. It sits to the right of every existing output, top-aligned at y 0, where an unlisted display goes. An error until P11 is in the core | the rig's `hyprctl output create headless` |
| `outputs.remove` | `{name}`: removes an output `outputs.create` made; its windows go where a disconnected output's go. An error for any other output | the rig's `hyprctl output remove` |
| `theme.set` | `Theme` (below): the seven roles of `hyprland-colors.lua.tmpl` and every key `fs-theme/src/chrome.rs` writes | `Theme` |

Events beside `state.changed`: `config.reloaded` after a settings reload,
on which the shell reads `binds.list` again, and `config.failed` with
`{error}` when the settings file was refused and the running settings stand. The shell sends `theme.set` on
every connect; the engine keeps the last one across a settings reload.

```ts
type Color = { cm: string; bitdepth: 8 | 10; sdrBrightness: number; sdrSaturation: number };
type Output = {
  name: string; make: string; model: string; enabled: boolean;
  x: number; y: number;              // logical, 0 when disabled
  width: number; height: number;     // the mode's pixels, 0 when disabled
  refresh: number;                   // Hz, 0 when disabled
  scale: number; transform: number;  // wl_output transform, 0 to 7
  mirrorOf: string;                  // "" when not mirroring
  vrr: boolean;
  modes: { width: number; height: number; refresh: number }[];
  color: Color;                      // cm "srgb" and bitdepth 8 without HDR
};
type Theme = {
  colors: {                          // "#rrggbb", from the shell's theme.json
    primary: string; primaryForeground: string; background: string; foreground: string;
    border: string; destructive: string; warning: string;
  };
  chrome: {
    rounding: number; blur: boolean; gapsIn: number; gapsOut: number;
    borderSize: number; shadow: boolean; shadowRange: number; shadowPower: number;
    shadowOffset: [number, number];
    // A colour is "#rrggbbaa", or a key of `colors` the engine resolves.
    borderColor: string; shadowColor: string; shadowInactiveColor: string;
    motion: {
      enabled: boolean;
      // the six families: spatialFast, spatial, spatialSlow, effectsFast,
      // effects, effectsSlow; curve is a cubic bezier's two control points
      families: Record<string, { curve: [number, number, number, number]; ms: number }>;
    };
  };
};
```

`Zen`, `Unzen` and `ZenRelease` have no method: under Shoji the engine owns
zen and the shell only asks for it and reads `workspaces[].zen`.

## 4. Overview

The compositor draws it with `COMPOSITOR.rendering.composition`: the output
zooms out to the workspaces stacked vertically, each its whole tape, every
window its live texture. The shell's layers stay where they are. niri's
behaviour is the reference:

- Opens on the bind, `overview.set`, four fingers up and the shell's hot
  corner (the shell calls `overview.set`). Escape, a click on empty space
  or the same gesture closes it.
- A click on a window focuses it and closes. A click on a workspace goes
  there.
- A window is dragged between columns, between workspaces, and onto the
  gap between two workspaces to open a new one there.
- Two-finger scroll and the arrow keys walk workspaces; typing does
  nothing (the launcher is the shell's).
- The zoom in and out rides the spatial clock; a gesture drives it 1:1.

Under Shoji the shell's own overview surface never opens.

## 5. Zen

A layout mode of one workspace, not a float: the zen window takes the
theme's zen size centred on the output, every other column slides off the
side it was on, the tape does not scroll while it holds. Toggling again, or
closing the window, slides the tape back with the window in its column at
the width it had. A floating window in zen returns to its float rect. The
shell reads `workspaces[].zen` to put the sidebar on its rail.

## 6. Overlays

An overlay is a named workspace that belongs to no output's stack and is
drawn over the focused workspace while shown, the workspace under it dimmed
0.6. The console is the only one (`formalshell-console`): the rule for
`dev.formalshell.console` maps it there, floating, hidden. `overlay.show`
brings a window's overlay onto the focused output and focuses it;
`overlay.park` hides it.

## 7. Drag and drop

- ShojiWM's drag views for data drags (the icon, the action badge, the
  fly-back on a refused drop), drawn in the shell's look.
- While anything is dragged, a window or data: holding it at the top-left
  hot corner opens the overview, holding it over a workspace there goes to
  it, holding it at a tape edge scrolls the tape, holding it over a window
  focuses that window so the drop can land in it.
- A window dragged by Super and the left button is lifted out of the tape
  and dropped into the column gap under the pointer, or onto a workspace in
  the overview.

## 9. Session and packaging

- The spec declares `formalwm` as a store package built from this repo's
  `wm/` on Tumbleweed, beside `hypr-dynamic-cursors` in
  `modules/linux/store.star`, and ShojiWM's portal
  (`xdg-desktop-portal-shojiwm`, `shojiwm.portal`) from the fork's rev.
- The greeter gets a second session entry. It starts `formalwm --tty`; the
  engine's startup, once its socket is up, runs
  `sh $XDG_CONFIG_HOME/formalwm/formalshell-start.sh` (written by
  `formalshell install`, the same line the Hyprland session runs): it
  unsets `HYPRLAND_INSTANCE_SIGNATURE SHOJIWM_SOCKET` in the user manager,
  which outlives a session, imports `WAYLAND_DISPLAY
  HYPRLAND_INSTANCE_SIGNATURE SHOJIWM_SOCKET XDG_CURRENT_DESKTOP
  XDG_SESSION_TYPE` and starts `formalshell.service`. The shell takes
  Shoji whenever `SHOJIWM_SOCKET` is set, Hyprland's variable or not.
- The engine reads `FORMALWM_START_LOCKED` from its environment: with `1`
  the session starts locked, as Hyprland does under `--locked-cmd`. Nothing
  is drawn but lock surfaces until a locker has locked and been unlocked,
  the start script runs all the same, and with no locker the session stays
  dark. The locked login sets it; the greeter's entry does not.
- `~/.config/formalwm` (the settings) comes from the spec's home tree.

## 10. Rig

The mac rig's fourth slot (`fstest3@fstestmac`) is Shoji's. `~/ShojiWM` is
the fork, `~/shoji-build.sh` builds it in a Tumbleweed container (the guest
has none of its headers), and it runs on that slot's vkms card. The engine
builds in the same container from a copy of `wm/` on the guest.
`dev/smoke.sh` takes the compositor from `FS_COMPOSITOR` (`hyprland`,
`shoji`): the launch, the generated config and every `hyprctl` read go
through one helper per compositor, so a leg is written once. Under Shoji
`$wmctl_bin` answers the part of hyprctl's command line the legs use
(`-j clients`, `layers`, `monitors`, `activewindow`, `workspaces`, `binds`,
`cursorpos`, and `dispatch` of the `hl.dsp.*` calls) from this socket, in
hyprctl's own JSON shapes; anything else fails the leg naming the call.
A leg says which compositors it runs under (`leg_<n>_compositors`,
`hyprland` when unset).
