# M77: earbuds, one panel for every vendor

Owner ask (2026-09-30): Nothing device support in the same panel as
AirPods, built as a vendor-agnostic system. Other brands come along where an
existing packaged CLI makes them cheap. The owner's own device is a CMF
Headphone Pro (Nothing sub-brand, model base B175), which ear-web drives
correctly for them.

## Decisions

- The AirPods panel, bar cell, IPC target and service become `earbuds`.
  No compat alias for the old `airpods` names: the panel name, the bar
  widget key, the IPC target and `bar.widgets.airpods.showLabel` are
  renamed outright (`bar.widgets.earbuds.showLabel`).
- One normalised device shape, rendered by one panel. A backend is a pure
  JS adapter (`shell/Earbuds/<vendor>.js`) that turns its source's raw
  state into that shape and turns a control change back into its source's
  command, plus a small QML object that owns the source (a file watch, a
  child process, a poll). The panel never branches on vendor.
- Shape, from `shell/Earbuds/model.js`:
  `{ key, backend, address, name, kind: "earbuds"|"headphone", connected,
  batteries: [{ id: "left"|"right"|"case"|"single", label, level, charging,
  inEar }], controls: [control], stateLine }` where a control is
  `{ key, kind: "choice"|"toggle"|"range", label, section, value, enabled,
  options: [{ value, label, icon }] | null, min, max, step }`.
  `choice` renders as a `ButtonGroup`, `toggle` as a `Switch`, `range` as a
  `Track`. A capability the device lacks is absent from `controls`, never a
  disabled stand-in and never an invented value.
- Backends in M77:
  - `airpods`: the existing omarchy-pods librepods daemon (status.json plus
    the control socket), moved behind the adapter unchanged in behaviour.
  - `nothing`: `nothingctl` (github.com/FormalSnake/nothingctl, MIT, the
    owner's own Rust CLI, packaged as `nix/nothingctl.nix` the way ttfx
    is). One `nothingctl watch -d <addr>` child per connected device while
    a consumer holds the service: JSON state lines on stdout, one command
    per line on stdin. Device discovery is `nothingctl list --json`, re-run
    when a Quickshell Bluetooth device's `connected` changes.
  - `soundcore`: `openscq30` from nixpkgs `open-scq30`. Its own device list
    (`paired-devices list --json`) crossed with BlueZ's connected devices;
    state polled with `device -a <mac> setting --get ... --json` every 30s
    while a consumer holds the service; sets are one call each.
  - `samsung`: `earbuds` from nixpkgs (LiveBudsCli), `earbuds status -o
    json` on the same poll, `earbuds set|enable|disable ...` for writes.
  - Sony: out. No packaged CLI exists (checked 2026-09-30).
- Product pictures (2026-10-23): a device carries `art`, a picture set
  under `FS_EARBUDS_ART` (`nix/earbuds-art.nix`: ear-web's Nothing and CMF
  pictures, librepods' AirPods ones, cut to 256 px webps). AirPods pick it
  by model number, Nothing by the Fast Pair model id nothingctl reports,
  falling back to the model's black. With a set, the panel leads with the
  product picture and gives each bud and the case a tile; without one
  (Soundcore, Samsung, AirPods Max) it keeps the glyph hero and battery rows.
- Several devices at once: the service lists every connected device across
  backends; the panel shows the most recently connected one and a device
  choice at the top when there is more than one.
- Honest states: no backend CLI on PATH drops that backend silently from
  discovery (every one is on the wrapper's PATH, so this only happens on a
  hand-built run); no connected device renders one dim `No earbuds
  connected` row.

## Safety (Nothing)

The owner has heard of Nothing devices bricked by wrong transports. The
shell never speaks the Nothing protocol itself: every byte goes through
`nothingctl`, which connects only by the service UUID ear-web uses, sends
only frames ear-web sends for that model (golden-tested), refuses unknown
models, and has no firmware, reset, rename, codec or ring command at all.
The shell sends `nothingctl` only the verbs its adapter allow-lists.

## Verification

- `tests/tst_earbuds_*.qml`: one test file per adapter against recorded
  fixtures, plus the shared model.
- `dev/smoke.d/earbuds.sh` `--earbuds`: PATH-shimmed `nothingctl` and
  `openscq30` fed from fixtures, the panel photographed with each device,
  an IPC `earbuds set` reaching the shim's own command log, and the
  AirPods path off a staged status.json.
- Real hardware (the owner's B175) is confirmed by the owner: first
  `nothingctl status` (reads only), then one ANC change.
