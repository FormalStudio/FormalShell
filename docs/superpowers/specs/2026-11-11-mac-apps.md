# Mac apps in the shell

Atoll (FormalStudio/atoll) runs Mac apps as ordinary Wayland windows. A Mac
app expects three things the shell does not have: a menu bar holding its
menus, a dock holding its icon, badge and dock menu, and a launcher that
knows what it is. This spec adds them.

The owner works from the keyboard. macOS is driven by the pointer, so its
chrome is too. Two rules follow, and they win over everything below:

1. **Pointer chrome is for Mac apps only.** The menu bar exists only while a
   Mac app has focus. The dock exists only while a Mac app runs (section 4).
   A session with no Mac app open has neither, and nothing a native app does
   today changes.
2. **Nothing needs the pointer.** Every menu item and every dock action is
   reachable from the launcher (section 5).

A window is a Mac app's when Hyprland reports its `xdgTag` as `atoll`, or
when its desktop entry carries `X-Atoll-BundleId` (an Electron app atoll
installed draws its own windows and has no tag). `fs_types::Window` gains
`mac: bool` from the first; the entry scan gains the second.

## 1. Transport

Both transports are existing desktop standards, so atoll implements nothing
private to this shell and another shell can read the same exports.

| What | Standard | Who serves |
| --- | --- | --- |
| The app's main menu | `com.canonical.dbusmenu` at an object path the app names | atoll |
| Which menu belongs to which app | `com.canonical.AppMenu.Registrar` (`RegisterWindow`, `UnregisterWindow`, `GetMenuForWindow`) at `/com/canonical/AppMenu/Registrar` | the shell |
| Badge, progress, attention | `com.canonical.Unity.LauncherEntry` `Update(uri, a{sv})`: `count`, `count-visible`, `progress`, `progress-visible`, `urgent` | atoll signals, the shell already listens (`services/activity.rs`) |
| The dock menu | the same signal's `quicklist`: a dbusmenu object path on the sender | atoll |

The registrar's window id is an X11 id, which a Wayland window does not
have. The shell therefore keys a registration by the caller's process: it
asks the bus for the sender's pid and matches that against the focused
window's pid. Atoll is one process per app and a Mac app has one main menu,
so the match is exact. The id is kept only to pair `RegisterWindow` with
`UnregisterWindow`; atoll sends 0. A registration from a process whose
windows are not Mac windows is stored and never shown (rule 1).

The KDE appmenu Wayland protocol was the other candidate. It needs the
compositor to carry it, Hyprland does not, and the shell is not the
compositor.

dbusmenu properties the shell reads beyond what the tray reads today:
`shortcut` (`aas`, for example `[["Control","Shift","S"]]`), and the
vendor keys `x-atoll-section` (a heading row) and `x-atoll-badge` (the dock
badge when it is not a number). Unknown keys are ignored by other hosts.

`AboutToShow(id)` is where atoll validates a menu (`menuNeedsUpdate:`,
`validateMenuItem:`), so the shell calls it before it shows or searches a
menu and reads the layout after.

## 2. Code layout

Per the untangle layout:

| Piece | Where |
| --- | --- |
| dbusmenu client for any `(service, path)`, split out of the tray's | `crates/fs-tray/src/dbusmenu.rs`; the tray uses it |
| Registrar interface and registrations | `crates/fs-tray/src/registrar.rs` |
| Service: owns the registrar name, follows focus, holds the focused app's menu tree and each app's dock menu | `services/appmenu.rs`, publishing `Diff::AppMenu` into `store.appmenu` |
| Menu bar cell | `surfaces/bar/cells/app_menu.rs` (`Builtin::AppMenu`, a `Custom` cell) |
| Sidebar card | `surfaces/sidebar/` beside the other cards |
| The open menu | `surfaces/tray_menu.rs`'s `Menu`, made to draw any `MenuNode` tree with a shortcut column, hosted by `wayland/tray_menu.rs`'s popout |
| Dock | drawing in `surfaces/dock/`, controller in `wayland/dock.rs` implementing `Owner` with its own `report` block |
| Launcher | `crates/fs-menu/src/providers/appmenu.rs` (menu commands) and additions to `apps.rs`, `actions.rs` |
| IPC | `ipc/appmenu.rs`, `ipc/dock.rs` |

Store writes are reactions in the services. Surfaces and the launcher model
return outs.

## 3. The menu bar

Present only while the held-focus window is a Mac window whose process
registered a menu. Otherwise the cell is not on the strip and the card is
not in the column.

**Strip (`layout: "bar"`).** `appmenu` is a builtin, in the default left
region straight after `active_window`. It draws the top-level titles in
the label style, each a hit target with the cell hover wash, the open one
carrying the open mark. The first title is the app's name in semibold (the
application menu), as on the Mac. On a vertical strip the titles do not
fit: the cell is one `menu` icon and opens the first-level list as a menu.

**Column (`layout: "sidebar"`, the owner's layout).** A Menu card under the
time card: the app's icon and name on its first row, then one row per
top-level title, the way NeXTSTEP stacked an app's menu at the screen's
corner. Collapsed to the rail it is the app's icon alone and opens the
first-level list. With too little height for every title the card keeps
its first row and that row opens the first-level list.

**An open menu** is the tray's menu card: `Role::Menu`, joined to the bar's
line under (or beside) its title, the same emerge and the same rows.
Additions: a shortcut column in keycaps at the trailing edge, heading rows,
and the pointer moving to another title while a menu is open switches
menus, as on the Mac. Submenus expand inline, indented, as the tray's do.
Disabled rows take the meta ink and no hover. A click sends dbusmenu
`Event(id, "clicked")` and closes the card; atoll performs the item on the
app's main thread.

Updates arrive as `LayoutUpdated` and `ItemsPropertiesUpdated`; the open
card patches in place.

IPC: `appmenu status` (the focused app, its titles, whether a menu is
open), `appmenu open <title>`, `appmenu close`, `appmenu activate <path>`
(`"File/Export/PDF"`, for a keybind).

## 4. The dock

`dock.show`: `"mac"` (default), `"always"`, `"never"`.

Under `"mac"` the dock's surfaces exist only while at least one Mac app
runs. With none running there is no surface and no hot edge. `"always"` is
for a pointer user who wants it for every app. Recommended default `"mac"`
over opt-in: a Mac app that sets a badge or asks for attention has nowhere
else to show it, and the dock costs a native-only session nothing.

It never takes space: `Layer::Top`, no exclusive zone, off screen at rest.
A one pixel strip on the bottom edge of each output (the hot corners'
surface and dwell, `dock.dwell` 150 ms) reveals it; it hides when the
pointer has been off it for 400 ms, or at once when a window takes focus by
a click. Under a fullscreen window the strip is unmapped
(`fullscreen.hideChrome`). `dock.position` is `bottom`, or the side the
sidebar is not on.

The dock is one card (`Role::Card`, the table's fill, border and radius),
centred, `screenPadding` off the edge, sliding in on the `Spatial` clock
and out on `SpatialFast`; with motion off it appears. Icons are 48, 9
apart. No magnification.

Contents, left to right: pinned apps (state.json `dockPins`, desktop ids),
a rule, then running apps that are not pinned. While it is shown it holds
native apps too, so the pointer can reach everything from one place.

| Mark | Source |
| --- | --- |
| Running dot under the icon | a window of the entry exists (`appicon::entry_for`) |
| Badge, top right | `Activity::badges()` count, or `x-atoll-badge` text |
| Progress bar across the icon's foot | LauncherEntry `progress` |
| Bounce | `urgent` rising, or Hyprland's urgent flag: three hops on the `Emphasized` clock, repeating every 4 s while urgent; with motion off the dot pulses between two inks. An urgent app reveals the dock for its first bounce. |
| Launching | the Activity launch item: the icon breathes until its window maps |

Click: focus the app's next window, or launch it (`launch::open`). Middle
click: a new instance. Right click: a menu card above the icon holding the
app's own dock menu (`quicklist`), its windows, its desktop actions, Keep in
Dock or Remove from Dock, and Quit.

Quit sends dbusmenu `Event` on the app menu's Quit item when the app
registered a menu (so `applicationShouldTerminate:` runs), else closes each
window.

IPC: `dock status`, `dock show`, `dock hide`, `dock pin <id>`,
`dock unpin <id>`, `dock menu <id>`.

## 5. Keyboard

**Menu commands in the launcher.** `menu summon appmenu` opens the launcher
on a Menu route listing every command of the focused Mac app: the title,
its path in the meta ink (`File › Export`), its shortcut in keycaps, a
tick where it is checked, disabled commands dimmed and not runnable.
Typing filters, Return runs. This is the Mac's Help search with the
keyboard first; the suggested bind is `SUPER + SHIFT + P`. From the root
query the same commands rank under apps while a Mac app has focus, so
`Space`, a few letters, Return runs one without the route.

**Dock actions in the launcher.** An app row's column (Tab) gains: Quit
(running), the app's dock menu items (running, with a quicklist), Keep in
Dock or Remove from Dock, and for a Mac app Uninstall. Show its windows and
the desktop actions are already there.

**Key equivalents.** Atoll performs a key equivalent itself when the key
reaches the app. Today atoll maps the Mac's Command to SUPER, and the
owner's Hyprland binds SUPER with Q, C, V, Z, F, O, S and more, so Copy,
Paste, Undo, Find, Open and Quit never arrive. Atoll changes its default:
the physical Ctrl key is Command and SUPER is Control, the convention of
every native Linux app, with `ATOLL_COMMAND_KEY=super` for an app that
needs a real Control (a terminal). The shortcut column names the keys as
this host types them. Settings gets the row once atoll reads the choice
from a file (follow-up 2).

## 6. Launcher entries

Atoll's desktop entries gain `Categories`, `Keywords` and
`X-Atoll-BundleId` (atoll's contracts.md). The shell:

- parses `MimeType`, `Categories` and `X-Atoll-BundleId` in the entry scan;
- marks a Mac app's row with a `MAC` meta label at its trailing edge;
- matches Mac windows by `StartupWMClass`, which is the bundle id and the
  window's class, so the first tier of `appicon::entry_for` already
  resolves them; `launch::match_windows` moves onto the same resolver;
- offers Uninstall for a Mac app fspec does not own, as
  `atoll uninstall <bundle id>` through Activity, beside fspec's own for
  one it does;
- filters a file's Open With targets to the entries whose `MimeType` holds
  the file's type, the rest under "Other apps".

Recent documents per app are a follow-up (6).

## 7. Legs

Each lands with its code and its `dev/smoke-map.toml` lines.

- `--appmenu-bar`: `dev/appmenu-stub.py` is a Wayland client that maps a
  window tagged `atoll` and, from the same process, registers a dbusmenu
  with the shell's registrar. Real pointer: the titles appear when its
  window takes focus and go when a foot window does; a click on File opens
  its card, a click on an item reaches the stub as `Event clicked` on that
  id; a checked item, a disabled one, a submenu and a shortcut read off
  `appmenu status` and the frame; a layout update from the stub lands in
  the open card. Under `--sidebar` the same on the column's card.
- `--appmenu-launcher`: `menu summon appmenu`, real keys typing part of an
  item's name, Return reaching the stub; the root query ranking it under
  apps; nothing listed with a foot window focused.
- `--dock`: no `formalshell:dock` layer with no Mac window; with the stub
  up, the strip on the bottom edge, a real pointer parked on it revealing
  the dock, a click on an icon focusing its window, a right click opening
  its menu with the stub's quicklist, a badge and progress sent as
  LauncherEntry updates read off `dock status` and the frame, `urgent`
  revealing it; the launcher's Quit action reaching the stub.
- With atoll built in the same slot (`FS_ATOLL=<binary>`), each leg runs
  against a real fixture app instead of the stub.

   About does nothing; Quit through the app menu is covered above.

5. The Mac window shadow drawn by the shell (atoll spec 4.4).

   dock menu, and as launcher rows).
7. Electron apps in Mac mode (atoll spec 12) registering through the same
   two interfaces.
8. An in-window menu bar in atoll for desktops with no registrar.
